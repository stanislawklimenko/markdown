# Критическая рефлексия и дальнейшие шаги

## Самая слабая часть решения
**Качество и покрытие RAG-поиска.**  
В PoC используется гибридный поиск по небольшой базе знаний (20 статей). В реальности база знаний может быть неструктурированной, устаревшей или противоречивой, что напрямую влияет на качество генерации. Также отсутствует механизм обновления индекса при изменении статей.

## Сделанные предположения
- Доля стандартных запросов = 40% — взята из бизнес-вводных, но не проверена на реальных данных.
- Английский язык — все запросы на английском, хотя сервис может иметь мультиязычную аудиторию.
- Доступность и стабильность LLM API — предполагаем, что внешний сервис работает с заданной задержкой и без сбоев.
- Структура данных: все тикеты содержат достаточно текста для классификации (нет коротких или пустых сообщений).

## Нерешённые риски
- **Галлюцинации LLM** — даже с шлюзом уверенности возможны ложноположительные срабатывания (высокая уверенность при фактической ошибке).
- **Изменение поведения пользователей** — если пользователи узнают об автоматизации, они могут менять формулировки, чтобы «обмануть» систему.
- **Масштабирование базы знаний** — при росте числа статей поиск может замедляться, а качество релевантности падать.
- **Юридические риски** — автоматические ответы могут быть расценены как официальные заявления компании.

## Что можно улучшить за 2 дополнительных дня
1. **Добавить базовый мониторинг** (логирование задержек каждого шага в Prometheus/Grafana) — 0.5 дня.
2. **Реализовать кэширование эмбеддингов для частых запросов** (Redis) — 0.5 дня.
3. **Написать интеграционные тесты для всех модулей** — 0.5 дня.
4. **Создать простой веб-интерфейс для агентов** (просмотр черновиков и эскалация) — 0.5 дня.

## Что доработать перед production-запуском
- **Разметка данных** — собрать и разметить не менее 10 000 исторических тикетов для обучения классификатора.
- **Детальное A/B-тестирование** — запустить shadow-режим на 5% трафика на 2 недели, сравнить метрики.
- **Механизм обратной связи** — дать пользователям возможность оценивать ответы и сообщать о неверных.
- **Политика безопасности** — согласовать с юридической службой список высокорисковых интентов, для которых автоответ запрещён категорически.
- **Резервирование LLM** — подключить второго провайдера (например, Anthropic) для fallback.

## Какие части системы не стоит автоматизировать полностью
- **Финансовые операции** (возвраты, списания, корректировки счетов) — всегда должны проходить через агента.
- **Безопасность аккаунта** (смена пароля по запросу, блокировка) — требуют дополнительной верификации.
- **Сложные кастомизированные вопросы** (интеграции, API, нестандартные сценарии) — где LLM часто даёт общие ответы.
- **Эмоционально заряженные обращения** (угрозы, жалобы на сотрудников) — требуют человеческого эмпатического ответа.

## Критерии остановки проекта по результатам пилота

Пилот считается провальным, если выполняется **хотя бы одно** из условий:

1. **CSAT упал ниже 3.8/5** (текущий 4.2) — значительное ухудшение качества поддержки.
2. **Deflection Rate < 20%** при ожидаемых 35% — автоматизация не даёт достаточной разгрузки.
3. **Reopen rate вырос до 15% и выше** — пользователи возвращаются с той же проблемой, что говорит о некачественном решении.
4. **Более 5% автоматических ответов получили жалобы** или были отмечены как «неверные».
5. **Любой инцидент с утечкой PII** или отправкой небезопасного контента (триггер для немедленной остановки).

Если хотя бы один из этих пунктов подтверждается статистически значимо (p < 0.05) через 2 недели пилота, проект возвращается на доработку или закрывается.
